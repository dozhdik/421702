# Корпоративная платформа блогов «ОМИС»

## 1. Назначение программы

«ОМИС» — локальное веб-приложение для публикации корпоративных статей и обмена знаниями между сотрудниками. Автор готовит материал, редактор рассматривает его и принимает решение о публикации или возврате на доработку. Опубликованные статьи доступны в общей ленте; зарегистрированные пользователи могут участвовать в обсуждениях.

Программа разработана на основе диаграмм и описания предметной области из [исходного отчёта](docs/reference/ОМИС%20Лаба%201%20Отчёт.pdf). Состав базовых UML-компонентов и соответствие их названий коду отражены в [инвентаризации](docs/uml_coverage.md) и [карте имён](docs/uml_name_mapping.md). Исходное текстовое техническое задание сохранено в [docs/spec/original_requirements.md](docs/spec/original_requirements.md).

## 2. Цель и задачи

Цель проекта — организовать единый процесс подготовки, согласования, публикации и обсуждения корпоративных материалов.

Для достижения цели программа решает следующие задачи:

- регистрация пользователей, вход в систему и разграничение прав;
- подготовка статей с рубриками, тегами и вложениями;
- сохранение черновиков и передача материалов на модерацию;
- рассмотрение статей и жалоб редактором;
- публикация, поиск и просмотр материалов;
- обсуждение статей, отправка реакций и жалоб;
- уведомление участников и формирование отчётов;
- сохранение данных между запусками приложения.

## 3. Пользователи и их возможности

| Роль | Основные действия |
| --- | --- |
| Гость | Просмотр опубликованных статей, поиск, регистрация и вход. |
| Читатель | Чтение статей, реакции, комментарии, ответы и жалобы. |
| Автор | Возможности читателя, создание и редактирование своих черновиков, отправка на модерацию, просмотр замечаний и удаление своих статей. |
| Редактор | Просмотр очередей статей и жалоб, изменение приоритета, публикация или возврат статьи с замечанием, рассмотрение жалоб. |
| Администратор | Управление рубриками, ролями и разрешениями, формирование отчётов. |

Доступ к операциям определяется назначенными правами и проверяется на сервере. Роли редактора и администратора разделены: административная роль сама по себе не предоставляет права модерации. Новому зарегистрированному пользователю назначаются права автора и читателя.

## 4. Функциональные возможности

### Работа со статьями

Автор создаёт черновик, вводит заголовок и текст, выбирает рубрику, указывает теги и при необходимости добавляет вложение. Предусмотрены ручное сохранение и автосохранение. Черновик можно открыть после повторного входа. При отправке на модерацию проверяется готовность материала к публикации.

В разделе «Мои статьи» отображаются материалы автора с фильтрацией по статусу. Для статей, возвращённых редактором, доступны замечания и повторная отправка после исправления. Автор также может удалить собственную статью после подтверждения. Для удаления чужого материала требуется отдельное разрешение `article.delete.any`.

Удаление является логическим: статья помечается полями `deleted_at` и `deleted_by`, исчезает из обычных списков, поиска и очереди модерации, а активная заявка закрывается. Связанные комментарии, реакции и протоколы сохраняются в базе. Восстановление через интерфейс не предусмотрено.

### Модерация и публикация

Редактор просматривает очередь материалов, меняет приоритет заявки, открывает статью и вложения. После одобрения статья публикуется; при возврате на доработку автор получает замечание. Редактор также рассматривает жалобы на комментарии и принимает решение об их обработке.

### Чтение и обсуждение

Публичная лента содержит опубликованные статьи. Предусмотрены поиск и фильтрация по автору, рубрике и тегу, а также постраничная навигация. На странице статьи отображаются содержимое, вложения, реакции и комментарии. Авторизованный пользователь может оставить комментарий, ответить в ветке, поставить реакцию или пожаловаться на комментарий.

### Администрирование и уведомления

Администратор управляет рубриками, ролями и разрешениями и может сформировать отчёт за период на основе сохранённых показателей публикаций, комментариев, реакций и просмотров. Уведомления отображаются получателю в отдельном разделе.

### Интерфейс по макетам ТЗ

Четыре основных экрана повторяют компоновку приложения H (с. 15–17): лента с рубриками и правой колонкой, редактор с полями и панелью форматирования над текстом, таблица модерации с проверкой выбранной статьи под ней и экран чтения с реакциями и обсуждением. На узком экране колонки складываются, таблицу можно прокручивать внутри её блока. Вместо опросов в ленте находятся быстрые ссылки на доступные разделы.

## 5. Архитектура и средства реализации

Приложение использует Python 3.11 или новее, стандартный WSGI-сервер и SQLite. Страницы формируются на сервере; оформление реализовано локальными CSS и JavaScript. Внешний сервер баз данных, платные сервисы и API-ключи для работы не требуются.

| Файл или каталог | Назначение |
| --- | --- |
| `omis_blog/domain.py` | Классы предметной области, состояния и правила переходов. |
| `omis_blog/controllers.py` | Обработка публикаций, модерации и других сценариев. |
| `omis_blog/storage.py` | Хранение сущностей и работа с SQLite. |
| `omis_blog/auth.py` | Аутентификация и проверка прав. |
| `omis_blog/presentation.py` | Представления и интерфейсы базовой модели. |
| `omis_blog/infrastructure.py` | Создание и связывание компонентов приложения. |
| `omis_blog/web.py` | HTTP-маршруты и формирование страниц. |
| `omis_blog/site.css`, `omis_blog/editor.js` | Оформление интерфейса и поведение редактора. |
| `scripts/` | Демоданные, миграция старой базы и служебные проверки. |
| `tests/` | Автоматические проверки модели, хранения и сценариев. |
| `docs/` | Материалы UML, решения, матрица тестов и отчёты. |

Пароли хранятся в виде хешей PBKDF2; формы защищены CSRF-токенами. Вложения хранятся в каталоге `uploads/` рядом с файлом базы данных.

## 6. Запуск

Для запуска нужен Python 3.11+. Выполняйте команды из каталога `lab2`, в котором находятся папки `omis_blog` и `scripts`:

```bash
cd ~/421702/sem5/OMIS/lab2
python3 -m omis_blog.main --db blog.sqlite --host 127.0.0.1 --port 8000
```

Откройте в браузере <http://127.0.0.1:8000/>. Для остановки сервера нажмите `Ctrl+C` в терминале. Параметр `--db` задаёт путь к файлу SQLite относительно текущего каталога.

**Состояние демоданных:** на момент составления отчёта файл `задание/seed_articles.json` отсутствует в рабочем дереве. Он необходим скрипту наполнения и автоматическому наполнению новой базы при первом запуске. Поэтому чистый запуск и часть тестов завершатся ошибкой, пока файл не восстановлен. Существующая база с учётными записями может использоваться для запуска; в ней уже должны быть необходимые данные. При неудачном первом наполнении новая база может оказаться частично заполненной, поэтому повторный запуск сам по себе не гарантирует полного наполнения.

Версия файла сохранена в коммите `a9c231a2`. Чтобы восстановить её для чистого запуска, из `lab2` выполните:

```bash
mkdir -p задание
git show a9c231a2:sem5/OMIS/lab2/задание/seed_articles.json > задание/seed_articles.json
```

После восстановления можно наполнить базу командой:

```bash
python3 -m scripts.seed_demo --db blog.sqlite
```

Наполнение рассчитано на повторный запуск без создания дубликатов демонстрационных статей. Рекомендуется проверить путь и сохранить резервную копию существующей базы перед работой с её данными.

Если порт 8000 уже занят, используйте другой порт, например `--port 8001`, либо завершите ранее запущенный сервер. Если процесс был приостановлен сочетанием `Ctrl+Z`, верните его в текущем терминале командой `fg`, затем остановите через `Ctrl+C`.

## 7. Демонстрационные учётные записи

Учётные записи создаются при успешном наполнении демонстрационными данными и предназначены только для локальной демонстрации.

| Роль | Логин | Пароль |
| --- | --- | --- |
| Автор | `author` | `author123` |
| Редактор | `editor` | `editor123` |
| Читатель | `reader` | `reader123` |
| Администратор | `admin` | `admin123` |

Для демонстрации можно войти автором, создать статью и отправить её на модерацию; затем войти редактором и опубликовать материал. После публикации статья появится в ленте, где читатель сможет оставить реакцию или комментарий.

## 8. Проверка программы

Для установки средств разработки и запуска проверок:

```bash
python3 -m venv .venv
. .venv/bin/activate
python3 -m pip install -e '.[dev]'
python3 -m pytest -q
ruff check omis_blog scripts tests
mypy omis_blog scripts
python3 scripts/check_english_identifiers.py .
```

Для JS-проверки автосохранения необходим Node.js: `node tests/js/editor_autosave.js`. Тесты создают временные базы, однако часть из них требует присутствия файла демоданных, указанного в разделе 6.

По [отчёту о доработке от 16.11.2026](docs/ui_ux_stage2_report.md), в рабочем дереве без файла демоданных полный набор завершился результатом **17 passed, 14 failed**; в отдельной временной копии с исходным файлом — **32 passed**. В той же проверке Ruff, Mypy и контроль английских идентификаторов прошли; для временной базы `integrity_check` вернул `ok`, нарушений внешних ключей не обнаружено. Эти результаты относятся к указанной проверке, а не к новому запуску тестов при подготовке данного README.

## 9. Текущее состояние и ограничения

Реализованы основные сценарии авторизации, работы со статьями, модерации, обсуждений, управления и логического удаления. Дополнительные направления из исходного задания — история версий, отложенные публикации, мультиязычность и разделение по филиалам — не входят в объём реализации.

Редизайн интерфейса остаётся на этапе проверки. Автоматические снимки доступны в [docs/screenshots/stage2/final](docs/screenshots/stage2/final/); полная ручная проверка клавиатурной навигации, контраста, длинного содержимого и пустых состояний ещё не проведена. Подробности и ограничения приведены в [отчёте UI/UX](docs/ui_ux_stage2_report.md) и [матрице тестов](docs/test_matrix.md).
