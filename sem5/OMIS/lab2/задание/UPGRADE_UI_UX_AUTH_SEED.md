### 0.1. Mandatory English-only source code and naming (supersedes older README wording)

**Hard requirement:** All source-code identifiers must be English, including class/interface/exception names, functions, methods, parameters, local and global variables, constants, enums and enum members, attributes, ORM fields, database tables/columns, package names, file names, route handler identifiers, CSS classes, HTML IDs, JavaScript identifiers, test names, and CLI options. Use conventional `PascalCase`, `snake_case`, and `UPPER_SNAKE_CASE`; keep clear domain meanings. Do not write transliterated Russian (`statya`, `rubrika`, `polzovatel`) or Cyrillic compatibility aliases.

**Only Russian user-facing content:** UI headings, controls, validation errors, notifications, and actual blog content may be in Russian. Store presentation strings in templates/i18n or other presentation-specific resources, not in domain/service constants. Technical comments, docstrings, internal log/event names, exception identifiers, error codes, SQL schema identifiers, and structured JSON keys must be in English. Preserve Unicode content in the database and rendered HTML.

The original specification is Russian and earlier `README.md` explicitly suggested retaining Cyrillic UML names. **This iteration overrides that naming rule only.** Preserve every *concept*, field meaning, public operation, relationship and workflow, but implement them under descriptive English names. Maintain `docs/uml_name_mapping.md` mapping every original UML element to its implemented English identifier and source file. No duplicates or nonfunctional aliases may be added just to satisfy old Cyrillic spellings.

If a live SQLite schema or persisted data already uses Cyrillic identifiers, migrate safely with backup, explicit migration steps, preserved primary keys/relations and rollback plan. Isolate necessary *legacy* names in a migration-only compatibility map; never introduce Cyrillic names in the resulting schema or runtime API. Never reset, overwrite, or delete an existing user database as a shortcut. If the current DB already uses English names, avoid pointless migrations.

Run `python3 scripts/check_english_identifiers.py .` after the refactor and add it to CI or the local quality gate. It checks Python identifiers, not user-facing Russian string literals. Also inspect DB schema, JavaScript, HTML IDs, CSS selectors, template variables and API/JSON field names. Refer to `ENGLISH_CODEBASE_POLICY.md` for the full contract.

## 1. Результат, который должен увидеть пользователь

### 1.1. Общий визуальный стиль

Интерфейс корпоративного блога на русском языке. Ориентир — чистый, современный редакционный продукт, а не учебный набор HTML-форм. Визуальные требования **не отменяют** доступность и функциональность.

- **Навигация:** аккуратная верхняя панель с названием «Корпоративный блог», ссылками «Лента», «Рубрики»/фильтры, «Мои статьи» (для автора), «Модерация» (для редактора), «Администрирование» (для администратора), входом/профилем справа.
- **Главная страница:** заголовок «Идеи, новости и знания нашей команды», заметный поиск и фильтры; 5 реальных демонстрационных материалов в карточках (адаптивная сетка), читаемые названия, краткое описание, рубрика, автор, дата, длительность чтения. Можно добавить выделенную первую статью.
- **Карточка статьи:** область обложки (если файлов нет — локальная CSS-обложка по рубрике, **не битая внешняя ссылка**), категория, заголовок, 1–2 строки анонса, автор/дата и кликабельный переход. Реальные счётчики, если показаны.
- **Страница статьи:** широкая, но ограниченная по длине строки колонка; заголовок, метаданные, форматированный текст с отступами и подзаголовками, реальные реакции, секция комментариев/ответов, жалобы, отображение статуса публикации только тем, кому положено.
- **Редактор:** понятное расположение полей (название, рубрика, теги, содержание, вложения), аккуратная индикация сохранения, сообщения валидации, отдельные кнопки «Сохранить черновик» и «Отправить на модерацию», предпросмотр при возможности без опасного рендеринга HTML.
- **Мои статьи:** личный список со статусами `Черновик`, `На модерации`, `Требует правок`, `Опубликовано`, `Архив/Снято` — согласно действующим enum. Фильтры, ссылка на редактирование доступных своих материалов, замечания редактора. Статусы проверяются на сервере.
- **Авторизация и регистрация:** две простые страницы или переключение вкладок, внятные сообщения об ошибках; после успешного входа показывается правильная навигация.
- **Редакторская очередь и админка:** единый дизайн-кит, читаемые таблицы/карточки, фильтры и контекстные кнопки, состояния «пусто», «ошибка», «загрузка», «успех». Не устранять существующие действия.
- **UI-состояния из ER/UML:** существующие классы UI-состояния и интерфейсы представлений должны оставаться задействованными, включая английские эквиваленты полей `current_theme`, `current_page`, `selected_filter`, `autosave_status`, `queue_filter`, где применимо.

### 1.2. Дизайн-система (рекомендация, адаптировать к текущей реализации)

- Светлая тема по умолчанию: фон `#F7F9FC`, основной текст `#172033`, поверхности `#FFFFFF`, границы `#E5EAF2`, акцент `#315CFD`, вторичный текст `#667085`. Темная тема **только если будет действительно работать** через существующий параметр темы; не рисовать нефункциональную кнопку.

- Учитывать клавиатуру и скринридеры: семантические `header/main/nav/article/form`, связанные `label`, видимый `:focus-visible`, понятные ошибки форм, корректные `aria-*` при необходимости; не полагаться только на цвет.
- Не добавлять тяжёлый фронтенд-фреймворк ради внешнего вида; адаптировать имеющиеся Jinja2/CSS/JS (либо текущий фактически используемый стек).

## 2. Регистрация, вход и право написать статью

**Главный пользовательский сценарий:** новый человек открывает сайт, создаёт собственную учётную запись, входит, нажимает «Написать статью», сохраняет свой черновик, отправляет на модерацию, видит его в «Мои статьи» и получает результат редактора. Самостоятельно публиковать без модерации нельзя.

### 2.1. Самостоятельная регистрация

- Добавь пользовательскую регистрацию, если её ещё нет: **ФИО, логин, пароль, подтверждение пароля**. Email — необязательное дополнительное поле, только если уже поддерживается схемой или легко добавить без нарушения UML. Не требовать внешней почтовой верификации для лабораторной.
- Проверки: непустые ФИО/логин, нормализация логина, уникальность без учёта регистра (в транзакции с ограничением БД), разумная длина полей; пароль не менее 10 символов и защита от слишком длинного ввода; подтверждение совпадает.
- Новый пользователь получает **роль `Автор контента`** с правами автора и читателя (включая чтение/комментарии/реакции). Если по текущей UML-схеме у аккаунта одна роль, добавь разрешения для роли автора, **не** переделывай её на две роли без необходимости. Новому пользователю никогда нельзя самоназначить `Редактор` или `Администратор`.
- Создай согласованные записи `User`, `UserAccount`, `ContentAuthor` и необходимые связи, **не дублируй секреты в открытом виде**. Если исходная UML-модель содержит два атрибута пароля, сохрани их смысл через английские API и безопасное хранение. Решение зафиксируй в `docs/decisions.md`.
- Регистрация — атомарна: при ошибке не остаётся частично созданных пользователя/роли/профиля. После успеха либо автоматически создаётся защищённая сессия с редиректом в «Мои статьи», либо предлагается войти — выбери единое поведение и зафиксируй в тестах (предпочтительно автоматический вход).
- Проверить существующие тестовые аккаунты: регистрация их не изменяет и не перезаписывает.

### 2.2. Вход, выход, сессии и доступ

- Использовать существующие маршруты и модель `UserSession`, не делать дублирующие cookie/таблицы пользователей.
- Хранить пароль только как надёжный хеш с солью (например, Argon2id через имеющуюся библиотеку, или PBKDF2/`scrypt` при отсутствии зависимости). Проверка выполняется в constant-time там, где применимо. Никогда не показывать хеши на странице.
- Сессионная cookie с `HttpOnly`, `SameSite=Lax`/`Strict` и `Secure` при HTTPS; обновление/ротация идентификатора сессии после входа, выход инвалидирует сессию на сервере. На локальном HTTP `Secure` настраивается корректно, иначе вход перестанет работать.
- CSRF-защита всех изменяющих состояние запросов, разумные ограничения частоты попыток входа, одинаково осторожные ошибки при неверном логине и пароле. Не раскрывать существование учётной записи лишними подробностями.
- Все права проверять сервером: гость не создаёт и не редактирует статьи; автор может менять только **свои** черновики и материалы со статусом «Требует правок»; отправлять на модерацию — только свою статью; `editor/admin` остаются привилегированными.
- Запретить передачу произвольных `author_id`, `role`, `status`, `published_at` от пользователя как основания полномочий: владельца и разрешённые переходы устанавливает сервер.
- Если чтение корпоративной ленты сейчас требует логина, **сохрани это правило**: гостю показывай аккуратную страницу входа/приветствия. Не открывай частный корпоративный контент анонимам без отдельного требования.

### 2.3. Путь нового автора (обязательно проверяется сквозным тестом)

1. Открывает `/` и переходит на «Регистрация».
2. Создаёт нового пользователя; получает корректную сессию.
3. Видит «Написать статью», «Мои статьи», «Выйти»; не видит действия модерации/администрирования.
4. Создаёт заголовок, текст, выбирает существующую рубрику, добавляет теги, сохраняет черновик.
5. Перезагружает страницу: данные черновика и владелец сохраняются.
6. Отправляет материал на модерацию и видит статус «На модерации».
7. Входит редактор и одобряет либо возвращает с замечаниями; автор видит результат после нового входа.
8. Другой автор не может редактировать эту статью ни через UI, ни напрямую через HTTP-запрос.

## 3. Наполнение: ровно пять новых опубликованных статей

Рядом с этим файлом находится `seed_articles.json`: **5 оригинальных полнотекстовых материалов на разные темы**, с рубриками, тегами, анонсами и датами публикации.

**Требования к интеграции:**

1. Не создавай отдельную неиспользуемую JSON-страницу или заглушки. Интегрируй в текущий `scripts.seed_demo` или в существующий официальный механизм наполнения БД. Используй фактическую доменную модель и репозитории; не обходи обязательные проверки/связи настолько, что нарушится UML.
2. Создай рубрики и теги, если их нет, и присвой статьи существующему демо-автору (или специально созданному демо-автору с корректной ролью и профилем). Создай необходимые `PublicationRecord` и `SearchIndex`, чтобы материалы были реально доступны в ленте и поиске. Все пять изначально имеют статус `Опубликовано`, но обычные новые пользовательские статьи проходят модерацию.
3. В каждой статье должен быть сохранён **весь текст**, рубрика, теги и анонс. Не заменяй текст `Lorem ipsum` или фразой «Тестовая статья».
4. Сохранить заданную последовательность по датам, показывать материалы в хронологической ленте по фактическим датам. Если у БД нет `slug`, использовать устойчивый seed-key на уровне скрипта/отдельной служебной таблицы, либо другую устойчивую идемпотентную стратегию. Не изменять старые опубликованные материалы.
5. **Идемпотентность:** повторный запуск seed не создаёт дубликаты, не сбрасывает пользователей, не меняет опубликованные пользовательские статьи и не перезаписывает самостоятельно изменённые записи. Лучше `insert-if-missing`, а не destructive reset.
6. Если текущий редактор/рендерер не поддерживает Markdown, безопасно преобразуй исходный Markdown в разрешённый HTML (санитайзер) **или** сохрани абзацы/заголовки средствами существующего рендерера. Нельзя отображать сырые HTML-теги пользовательского ввода через небезопасный `|safe`.
7. На главной странице видны все пять статей, а фильтры по рубрикам/тегам, поиск и переход на каждую статью работают. Допустимо использовать CSS-обложки вместо внешних фотографий.
8. Метрики просмотров/реакций/комментариев не показывать как искусственно сочинённые реальные данные. Если создаются демонстрационные комментарии, обозначать их как демоданные и добавлять через штатный API/модель.

## 4. Порядок реализации

### Этап 0. Аудит текущей реализации и английских идентификаторов
- Пройди реальные маршруты, проверь сессии и права; создай `docs/ui_ux_baseline.md` со списком текущих страниц, недостатков и повторно используемых классов. Отдельно инвентаризируй все кириллические программные идентификаторы и составь `docs/uml_name_mapping.md`.
- Сделай бэкап схемы/миграцию, **не удаляй** пользовательскую БД.

### Этап 1. Рефакторинг на английские идентификаторы и регистрация
- Переименуй кириллические классы, методы, переменные, поля и схему БД (только если это требуется), исправь импорты/тесты/DI и проверь целостность сохранённых данных. Затем реализуй регистрацию поверх прежней модели пользователя, роль автора с правами читателя, корректное создание сессии, «Мои статьи», авторство и фильтры.
- Проверки: регистрация, уникальность, запреты RBAC, восстановление после перезапуска БД.

### Этап 2. Наполнение базы
- Подключи `seed_articles.json` к `scripts.seed_demo`, безопасно конвертируй формат текста, проверь полные записи, категории, теги, индекс, протоколы публикаций и повторный seed.

### Этап 3. Обновление UI/UX
- Единые layout/навигация, главная с карточками, читаемая публикация, формы авторизации, создание/редактирование и «Мои статьи».
- Сохранить и улучшить редакторскую очередь, комментарии/реакции/жалобы, уведомления и админку.
- Протестировать адаптивность и доступность, работать без CDN и внешних картинок.

### Этап 4. Приёмка
- Прогнать `pytest`, `ruff check`, `mypy` и `python3 scripts/check_english_identifiers.py .` по фактическим командам репозитория; устранить регрессии.
- Проверить работу браузерных сценариев, включая ошибки форм и пустые состояния.
- Обновить README: регистрация нового пользователя, тестовые аккаунты, `seed_demo`, запуск, тестирование.
- В `docs/uml_coverage.md` и `docs/test_matrix.md` обновить пути/тесты, если затронуты классы/сценарии; описать архитектурные решения в `docs/decisions.md`.
