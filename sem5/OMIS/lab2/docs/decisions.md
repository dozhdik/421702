# Решения при неоднозначностях

1. **Источник ТЗ.** Каталог `docs/spec/` в полученном проекте отсутствует. Исходным ТЗ считается PDF `docs/reference/ОМИС Лаба 1 Отчёт.pdf`, на который ссылается README. Инвентаризация основана на изображениях A.1–A.7 и E.1–E.5 из него (стр. 4–6, 11–13).
2. **Страницы F исключены.** Раздел 6 исходного описания (стр. 3) и F (стр. 13–14) задают направления развития, которые README §0 и §10 прямо исключают. Одобрение публикует сразу, без планировщика (BPMN стр. 7).
3. **Пароль у Пользователь и УчетнаяЗапись.** Оба UML-поля остаются доступными, но представляют один и тот же парольный хеш; физическое хранилище содержит только один экземпляр хеша (A.2/E.1).
4. **Непоследовательная кардинальность очереди.** A.4 рисует связь статья 1 — заявка N, E.1 показывает статью 1 — заявка 1. Повторная подача требует сохранения истории, поэтому хранится несколько заявок на одну статью, при этом активная заявка только одна (A.4, стр. 5; E.1, стр. 11).
5. **Представления.** E.3 задаёт четыре интерфейса и абстрактное базовое представление, но не именует конкретные реализации. Они получат явные классы-адаптеры HTML. Состояния A.7 остаются отдельными типами (стр. 6, 12).
6. **Локальный стек.** В исходном окружении отсутствуют FastAPI и SQLAlchemy. README §6 разрешает эквивалентный web-стек при сохранении UML. Использованы `wsgiref`, `sqlite3` и стандартная библиотека Python; `pytest`, `ruff`, `mypy` применяются только для проверок. Это исключает сетевые зависимости при обычном запуске.
7. **Охват отчёта.** Единственное числовое UML-поле `метрикаОхвата` хранит количество открытий опубликованных статей за период; дополнительные агрегаты публикаций, комментариев и реакций хранятся отдельно (E.1, стр. 11; README §1.3).
8. **Жалобы.** Открытая очередь для редактора содержит жалобы только после трёх уникальных открытых жалоб на комментарий. Это соответствует порогу на sequence-диаграмме (стр. 10); ранее закрытые жалобы не создают новый порог.
9. **Неполный черновик и внешние ключи.** Пока связь не выбрана, поле идентификатора хранится как `NULL` в SQLite и читается как пустая строка в модели. Выбранные связи получают внешние ключи. Для циклической пары пользователь—аккаунт внешний ключ направлен от аккаунта к пользователю; обратная уникальность проверяется частичным индексом (A.2, стр. 4; E.1, стр. 11).
10. **Состояние UI.** Шесть сущностей A.7 реализованы типизированными классами; состояние ленты, редактора, кабинета и окна чтения хранится отдельно для каждой активной сессии в памяти web-приложения. Сама сессия хранится в SQLite (A.7, стр. 6; README §2.3).
11. **Имена кода.** `задание/ENGLISH_CODEBASE_POLICY.md` меняет правило именования исходного README. Все классы, поля, операции и связи A/E сохранены по смыслу, но программные имена и схема БД английские. Полная карта — `docs/uml_name_mapping.md`; кириллические ключи остались только в карте миграции. Значения статусов и вердиктов в ядре — английские коды; русский текст выводит `omis_blog/localization.py`.
12. **Миграция.** `scripts/migrate_legacy_db.py` создаёт резервную копию, переименовывает таблицы/столбцы и enum значения в одной транзакции, проверяет количества строк, ID и хеши аккаунтов, внешние ключи и `integrity_check`. При сбое транзакция откатывается. `Database` отказывается открывать старую схему до явной миграции.
13. **Самостоятельная регистрация.** Один аккаунт получает роль автора с правами `article.write`, `feed.read`, `comment.write`, `reaction.write`; создаются `User`, `UserAccount`, `ContentAuthor`, `Reader` в одной транзакции. Логин защищён уникальным индексом `lower(login)`. Хеш PBKDF2 со случайной солью хранится в аккаунте; UML-атрибут пользователя отражает хеш в памяти. После регистрации и входа ID сессии и CSRF-токен ротируются, после выхода запись сессии удаляется. Лента остаётся публичной, как в исходном приложении.
14. **Пять материалов.** `scripts/seed_demo.py` читает `задание/seed_articles.json`, использует устойчивые `seed_key`/UUID, добавляет только отсутствующие статьи, рубрики и теги, публикует через `PublicationController`, сохраняет `PublicationRecord` и `SearchIndex`. Прямой запуск приложения вызывает seed только для БД без аккаунтов; пользовательские БД не наполняются автоматически. Полный Markdown остаётся в `Article.content`; web-слой экранирует HTML и преобразует заголовки и абзацы. Даты публикации из JSON используются в ленте.
15. **UI.** `omis_blog/site.css` задаёт общие компоненты и адаптивность; `WebApp` использует состояния A.7 и представления E.3. Темная тема не вводилась: исходный параметр темы не имел работающего переключателя. Обложки генерируются локальным CSS.
16. **Мягкое удаление статьи.** Дополнительные поля `Article.deleted_at` и `Article.deleted_by` расширяют базовый UML-класс без удаления его полей и связей. Новые и существующие SQLite схемы получают поля через `Database.create_schema`; перед изменением рабочей БД создана копия в `backups/`. Удаление статьи и закрытие активной заявки модерации выполняются одной транзакцией. Общая лента, поиск, личный кабинет, очередь материалов и жалоб отфильтровывают удалённые статьи. Комментарии, реакции, индексы и протоколы сохраняются; повторная запись удалённой статьи запрещена. Веб-маршрут требует CSRF, а владелец проверяется по профилю автора; чужая статья требует отдельного права `article.delete.any`. Для вызова общего метода репозитория без пользователя `deleted_by` остаётся пустым, а пользовательские запросы всегда записывают ID пользователя.

## UI/UX Stage 2

Для оформления использованы серверные HTML-компоненты и локальные CSS-переменные. Выделенная публикация выбирается из существующей выдачи; счётчики и данные модерации берутся из базы. Права и CSRF остаются на сервере. Промежуточные снимки интерфейса сохранены в `docs/screenshots/stage2/after/`; до завершения приёмки требуется проверить доступность и обработку ошибок форм.
