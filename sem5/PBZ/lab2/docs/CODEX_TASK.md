## 2. Реальный объём задания по методичке

Источник: «Лабораторная работа № 2. Приложения для работы с базами данных», **вариант 9, стр. 10**.

**Предметная область:** страховая организация заключает договоры с физическими лицами и организациями. Для организации оформляется коллективный договор со списком застрахованных работников (ФИО, возраст, категория риска). Организация характеризуется кодом, полным и кратким наименованиями, адресом, банковскими реквизитами, специализацией. У коллективного договора есть дата заключения, дата окончания, выплаты по категориям сотрудников и выплаты по страховым случаям. У страхового агента — ФИО и паспортные данные; по каждому договору назначается один агент (у агента может быть много договоров).

**Обязательные операции, перечисленные в варианте:**

1. Добавление / редактирование / удаление **организаций**.
2. Добавление / редактирование / удаление **страхуемых сотрудников**.
3. Добавление / редактирование / удаление **страховых агентов**.
4. **Отчёт 1:** действующие договоры выбранной организации на заданную дату — название организации, адрес, дата, номер договора, начало и конец действия.
5. **Отчёт 2:** агенты, ведущие действующие договоры выбранной организации на заданную дату — дата, название страховой фирмы, ФИО и контактный телефон агента. Один агент не должен дублироваться, если у него несколько договоров.
6. **Отчёт 3:** размеры страховых выплат по категориям сотрудников на заданную дату — дата, категория, сумма. Если суммы для одной категории отличаются по разным договорам, не смешивай их; можно показывать номер договора для ясности.

**Чтобы обязательные функции можно было продемонстрировать**, также нужны минимальные консольные операции просмотра/создания/редактирования/удаления коллективных договоров, привязки сотрудников к договорам и управления размерами выплат по категориям. В описании предметной области упоминаются индивидуальные страхователи и страховые случаи, но отдельные обязательные операции для них не расписаны. Если поддержка этих сущностей уже работоспособно реализована — сохрани и сделай доступной через простой CLI; **не строй ради неё большую новую подсистему и не задерживай обязательные функции и три отчёта**. При необходимости сделай минимальную реализацию только для сохранения данных, прямо названных в описании.

**Общее требование к отчёту** пособия упоминает «основные окна приложения», но в данном проекте пользователь специально выбрал **консольную реализацию**. **Не делай GUI ради этого пункта**; для отчёта можно подготовить скриншоты меню и результатов в терминале и кратко пояснить выбор интерфейса. Сам Word/PDF-отчёт не создавай без отдельного запроса.

## 3. Требования к консольному приложению

**Один простой вход:** `python3 main.py` из каталога проекта.

- При запуске инициализировать базу SQLite, не стирая существующие данные.
- Показать понятное **текстовое меню на русском языке** с нумерованными пунктами; управление через `input()`, вывод через `print()`.
- Предлагаемая структура главного меню (можно немного упростить, но не терять доступ к функциям):

```text
=== УЧЁТ ДОГОВОРОВ СТРАХОВАНИЯ ===
1. Организации
2. Страхуемые сотрудники
3. Страховые агенты
4. Коллективные договоры
5. Суммы выплат по категориям
6. Отчёт: действующие договоры организации
7. Отчёт: агенты организации
8. Отчёт: выплаты по категориям
9. Заполнить БД демонстрационными данными
0. Выход
Выберите пункт:
```

- В разделах организаций, сотрудников и агентов сделать простое подменю: **показать список / добавить / изменить / удалить / назад**. Для договоров — дополнительно показать участников, добавить или удалить сотрудника, работать с категориями выплат.
- Пользователь вводит значения по очереди; показывать, что именно нужно ввести. Если нужна ссылка на организацию/агента/сотрудника — сначала дать возможность просмотреть список с ID.
- Ввод даты — `YYYY-MM-DD`; проверять настоящие календарные даты, порядок дат, существование ID, обязательные строки, положительный возраст и неотрицательную сумму. Ошибки сообщать понятным текстом **без падения программы и без traceback для обычного неверного ввода**.
- Все меню повторяются до команды «Назад» / «Выход». **EOF (Ctrl+D) и Ctrl+C** обрабатывать корректно, закрывать ресурсы.
- Перед удалением показывать объект и запрашивать подтверждение. Не допускать молчаливого каскадного удаления значимых связанных данных.
- Три отчёта принимают нужные параметры из консоли и выводят **читаемые текстовые таблицы/списки**, а если данных нет — понятное сообщение. Для отчёта 3 код организации может быть необязательным дополнительным фильтром.
- **Никаких `tkinter`, `ttk`, `PyQt`, `PySide`, web-серверов, HTML, Flask/FastAPI, сложных TUI-библиотек** и дополнительных зависимостей ради интерфейса. Можно использовать `sqlite3`, `datetime`, `textwrap`, `unittest` и прочую стандартную библиотеку.
- Не добавляй авторизацию, роли, сеть, REST API, Docker, ORM, сложную структуру пакетов и другие функции, которых пользователь не просил.

## 4. Сохрани рабочие части исходного проекта

Исходный проект уже имеет:

- `models/database.py`: `sqlite3`, `get_connection()`, `init_database()`; таблицы `Organization`, `Employee`, `Agent`, `Contract`, `ContractEmployee`, `Payout`.
- Модели `Organization`, `Employee`, `Agent`, `Contract`, `Payout` с CRUD и валидацией.
- `Contract.add_employee()`, `remove_employee()`, `get_employees()`.
- Три SQL-запроса-отчёта в `Contract`: `dated_org_contract()`, `dated_org_agent()`, `payout_date()`.
- `models/seed.py`: `seed_database()` с демонстрационными записями.

Используй существующий API там, где он корректен. **`main.py` в исходном архиве пустой** — главная работа состоит в подключении существующих методов к нормальному консольному меню. Исправляй реальные проблемы, а не делай из лабораторной большой новый проект.

Минимальные правила целостности:

- Уникальность кода организации и номера договора; каждый коллективный договор относится к одной организации и одному агенту.
- В договор можно включить только сотрудника той же организации; один сотрудник не должен быть добавлен в один и тот же договор дважды.
- Интервал действия договора включает начало и конец: `conclusion_date <= selected_date <= end_date` (дату заключения трактовать как начало, если нет отдельного поля).
- Выплаты по категориям должны однозначно относиться к договору; не путать **размер выплаты, установленный договором**, и **фактическую выплату по страховому случаю**.
- Использовать только параметризованные SQL-запросы и открывать SQLite с включёнными внешними ключами. Не ломать существующую базу.
